# 测试工作流程规范（dyd-test 内化版）

主线：需求评审 → 用例设计 → 提测准入 → 测试执行 → 缺陷闭环 → 发布审批与上线 → 上线后收尾。
每阶段有明确输出物与可判断的出口条件。

## 三条前置底线

- 需求不清晰、存在矛盾或无法验证：澄清后再进入开发与测试。
- 阻断级缺陷未闭环、遗留缺陷未明确处理人：不发起线上发布审批。
- 环境、增量 SQL、账号权限未就绪：不开始正式执行用例，避免把环境问题误判为功能缺陷。

## 需求评审

- 会前完整读文档与原型，拆可验证条目；准备要点含：核心需求点、关键计算规则、测试关注点、待确认事项。
- 数据类口径（金额/返点/利润/消耗/应收）必须在评审阶段锁死归属，口径差异会直接改变报表数字。
- 待确认项按责任人跟踪；答复未落地前对应用例标"待定"，不按推测验收。
- 出口：需求清晰、可实现、可验证；每项口径疑问有答复人或跟踪人。

## 用例设计

- 按 [PRD 验收记录](acceptance-contract.md) 拆独立验收点并保留出处。单条用例写清输入、步骤、逐项预期和测试数据；按风险覆盖正常主流程、边界值、异常失败、角色可见性与回归。
- 涉及金额等口径单独设计数据核对方案：源表核对、新旧口径对比、边界样本抽样（0 值、负数、跨月、特殊客户）。
- 录入禅道并同步开发群。出口：覆盖五类场景，未覆盖项和依赖项有说明。

## 提测准入

- 提测文档含版本号、更新摘要、测试点、增量 SQL；SQL 由测试在测试环境执行并核对，执行前后确认数据状态。
- 检查：版本冒烟可通、文档一致、SQL 已核对或有不适用依据、账号角色可确认。登录后以只读方式找到模块入口，核对路由、角色和页面特征；禅道未接入时如实记录。
- 冒烟不通过退回研发；不带着不可用版本开始用例。出口：冒烟通过、环境可用、SQL 已执行。

## 测试执行

- 顺序按风险：主流程与数据口径 → 分支/边界/权限 → 回归。数据类先核对数据再验页面；权限类先确认角色矩阵与入口。
- 非功能问题（无入口、权限未配、环境不可用）记录为阻塞项，不并入缺陷统计；端到端验收延后补做，不默认通过。
- 执行数与通过率以禅道测试单为准；未打通时如实说明，不凑数字。

## 缺陷管理

- 流转：提单（复现步骤/预期/实际/影响/模块，附截图与请求参数）→ 指派研发 → 已解决 → 测试回归 → 关闭或激活重提。
- 回归范围覆盖同一链路相邻场景，防止修一处坏一处。

|等级|定义|典型情形|放行要求|
|---|---|---|---|
|P0|安全或生产级严重事故|越权、资金/结算错误、绕过约束、敏感信息泄露|立即阻断发布，修复并回归后方可上线|
|P1|核心链路失败或高概率误导|主流程不可用、金额展示错误、无法提交|修复并回归后放行|
|P2|重要能力不稳定|筛选失效、字段回显错误、报表缺字段|上线前修复或产品书面让步接收|
|P3|体验或展示问题|文案错误、字段顺序、样式异常|登记跟踪，可随后续迭代修复|
|P4|低风险优化项|交互冗余、提示不明确|排入后续优化清单|

- 严重程度按业务影响判定，不按发现难度或控制台日志数量判定。
- 有副作用的缺陷复现前先恢复或准备独立测试状态，禁止盲目重复写入；无法安全重现则保留首次证据标"待复现"。

## 发布审批与上线

- 审批通过后才发布；发布内容按业务可读方式写清改动、影响范围、需求/缺陷编号。
- 上线后验证核心链路：主流程能走通、关键数据能出来、权限入口可见；数据类核对线上首日与测试环境差异来源。

## 上线后收尾

- 数据巡检：上线后一周每日核对核心口径；出现过中断的口径巡检不短于一周。
- 权限按最小必要配置；上线前完成培训。周报写清统计窗口与数据缺口，统计不出的字段写"未接入，不作估算"。

## 执行记录口径

用例执行数与通过率以禅道测试单统计为准；未接入禅道时明确标注为 dyd-test 本地统计。
